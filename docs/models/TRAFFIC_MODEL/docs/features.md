# План развития модуля TRAFFIC_MODEL

> Ответственный: Кутенков Андрей | Обновлено: 2026-10-17

Идентификаторы глобально уникальны: `FEAT-TRF-NNN`. Прежний локальный FEAT-001..004 соответствует FEAT-TRF-001..004; порядковые номера и смысл предложений сохранены. Общая крупная фича — `FEAT-INT-001`, спецификация [INT-MF-001 v1.0](../../integration_report.md). Все интерфейсы в ней — проектные.

## 1. Предложения для своего модуля

### FEAT-TRF-001 — Единый контракт генерации Packet с UE и интервалом
- **Статус:** идея; черновик уточнён по коду, согласование изменений не получено.
- **Проблема сейчас:** PacketManager имеет реальный API с current_time как концом окна; creation_time получается дробным. Для нового контракта нужны адаптер времени и сохранение deadline.
- **Цель:** Адаптер приводит выход PacketManager к TrafficResult; единицы времени нормализуются на границе адаптера.
- **Предлагаемое изменение:** Адаптер приводит выход PacketManager к TrafficResult; единицы времени нормализуются на границе адаптера.
- **Входит / не входит:** собственный адаптер, внутреннее состояние и тесты TRAFFIC_MODEL; изменения SimulationManager, RNG и UE_MODULE выполняют их владельцы. Переписывание математических формул не входит.
- **Входы и выходы:** черновик INT-MF-001, разделы 3–6; адаптер принимает StepContext и снимок UE, выдаёт результат своего модуля. Для file вход — готовые записи; для model — параметры и выделенный RNG.
- **Зависимости:** SimulationManager — время и маршрутизация; UE_MODULE — ID и применение; RNG — воспроизводимые потоки. Запросы перечислены ниже в разделе 2 настоящего файла.
- **Шаги:** 1) использовать выполненную сверку исходников и результаты audit; 2) согласовать соответствующую часть INT-MF-001; 3) реализовать собственный адаптер/изменение; 4) выполнить проверку ниже и общую интеграционную матрицу.
- **Проверка готовности:** Все времена пакетов попадают в [t_start_ms,t_end_ms); два UE не обмениваются пакетами; packet_rate=0 обрабатывается по согласованной политике без деления на ноль.
- **Риски и вопросы:** действующие сигнатуры проверены; до изменения сохранить поведение базового сценария и согласовать правила времени, RNG и lifecycle.
- **Ссылки:** [спецификация](../../integration_report.md), [ревизия](audit.md).

### FEAT-TRF-003 — Изоляция RNG и ON/OFF/MMPP-состояния по UE
- **Статус:** идея; черновик уточнён по коду, согласование изменений не получено.
- **Проблема сейчас:** ON/OFF и MMPP сохраняют состояния по UE, но используют общий np.random; reset_ue очищает профиль, а историческая статистика сохраняется.
- **Цель:** Разделить потоки RNG и фазовые состояния по UE/bearer; явно определить очистку reset_ue и статистики.
- **Предлагаемое изменение:** Разделить потоки RNG и фазовые состояния по UE/bearer; явно определить очистку reset_ue и статистики.
- **Входит / не входит:** собственный адаптер, внутреннее состояние и тесты TRAFFIC_MODEL; изменения SimulationManager, RNG и UE_MODULE выполняют их владельцы. Переписывание математических формул не входит.

- **Зависимости:** SimulationManager — время и маршрутизация; UE_MODULE — ID и применение; RNG — воспроизводимые потоки. Запросы перечислены ниже в разделе 2 настоящего файла.
- **Шаги:** 1) использовать выполненную сверку исходников и результаты audit; 2) согласовать соответствующую часть INT-MF-001; 3) реализовать собственный адаптер/изменение; 4) выполнить проверку ниже и общую интеграционную матрицу.
- **Проверка готовности:** Удаление UE=1 не изменяет фазу UE=2; повторный запуск с тем же seed воспроизводит пакеты.
- **Риски и вопросы:** действующие сигнатуры проверены; до изменения сохранить поведение базового сценария и согласовать правила времени, RNG и lifecycle.
