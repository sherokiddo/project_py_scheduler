### BUG-SCH-001 — Двойное нулевое обновление throughput у незапланированного UE
- **Объект:** `PyScheduler/SCHEDULER.py::SchedulerInterface._process_buffers` (:880; ветки :912–913 и :937–938)
- **Категория:** подозрение на баг
- **Наблюдение:** UE без выделенных RB, но с живым буфером получает `UPD_DL_THROUGHPUT_BPS(0)` дважды за TTI: ветка `allocated_rbs == 0` (:912) не делает `continue`, затем срабатывает ветка `max_bytes <= 0` (:937). Аналогично UE без буфера: :913 + :924.
- **Доказательство:** замер на `ae9db40`: сценарий README §4, у UE2 заранее выставлен `average_throughput = 1 000 000`; инструментированный счётчик вызовов — `UE2: 2 вызова UPD(0)`; результат `average_throughput = 996 004 = 1e6·(1−0.002)²` вместо `998 000 = 1e6·(1−0.002)`.
- **Влияние:** EWMA-среднее незапланированных UE затухает вдвое быстрее — знаменатель PF-метрики (`_calculate_priorities` :2118) «остывает» некорректно; на длинных прогонах искажает справедливость PF/FD_PF.
- **Как проверить:** воспроизвести замер выше; уточнить у владельца модуля: двойной шаг — намеренное «остывание» или пропущенный `continue` в ветке :912.
- **Статус:** подтверждено замером на `ae9db40`; **закрыт на `6c0aae2`** (PR #39): ветка `allocated_rbs == 0` получила `continue` (:919) вместе с обновлением `qci_tput_tracker`, второй нулевой шаг исчез. Контрольный замер на `6c0aae2`: тот же сценарий, `average_throughput` UE2 = `998 000 = 1e6·(1−0.002)` — один шаг EWMA.
- **Связь:** issue пока нет; учесть в [FEAT-SCH-005](features.md#feat-sch-005) (PF)

### BUG-SCH-002 — Невалидный CQI не затирает устаревшую запись карты
- **Объект:** `PyScheduler/SCHEDULER.py::SchedulerInterface._refresh_cqi` (:504; WB-ветка :527–541, SB-ветка :546–553)
- **Категория:** вопрос
- **Наблюдение:** CQI вне [1..15] игнорируется — существующая запись `cqi_map` сохраняет старое значение без ограничения по возрасту; пустой `sbb_cqi` старое значение также не очищает. Метки `last_wb_update`/`last_sb_update` пишутся, но нигде не проверяются на устаревание.
- **Доказательство:** чтение кода :527–553; docstring «Invalid CQI (вне [1-15]) игнорируются» (:518).
- **Влияние:** при прекращении отчётов UE планируется по последнему корректному CQI неограниченно долго; в реальной сети периодичность отчётов задаётся CQI-ReportConfig (TS 36.331), у нас интервалы `wb/sb_cqi_upd_interval` (:336–337) есть, а контроля свежести нет.
- **Как проверить:** уточнить у владельца модуля: модель «последний валидный отчёт» — намеренная? Если да — нужен ли параметр максимального возраста записи. Настройка отчётности CQI уже запрошена в issue #28.
- **Статус:** подтверждено (факт в коде); баг/не баг — оценивает владелец модуля
- **Связь:** issue #28 (настройка CQIReport)

### BUG-SCH-003 — FD-алгоритмы выбирают по SB CQI, а ёмкость гранта считается по WB
- **Объект:** FD `_allocate_pdsch` (FD_BCQI :2269, FD_FGS :2423, FD_PF :2631 — SB-выбор :2661–2667) vs `_process_buffers` (:927 — `cqi = self._get_wb_cqi(ueid)`)
- **Категория:** вопрос (рассогласование модели)
- **Наблюдение:** на этапе 6 FD-планировщики выбирают победителя по SB CQI конкретного RBG, на этапе 7 вместимость выделенного считается по WB CQI.
- **Доказательство:** чтение кода (ссылки выше).
- **Влияние:** UE мог получить RBG именно потому, что его SB CQI на этих участках выше WB, но извлечение из буфера и статистика throughput считаются по WB — оценка и факт расходятся; EWMA-знаменатель PF следующего TTI строится на WB-оценке.
- **Как проверить:** FD-сценарий с контрастными SB CQI: сравнить `dl_capacity_bits_sum_tti` при расчёте по WB и по среднему SB выделенных RBG.
- **Статус:** подтверждено (факт в коде); величина влияния — гипотеза
- **Связь:** [FEAT-SCH-002](features.md#feat-sch-002)/[FEAT-SCH-003](features.md#feat-sch-003); в srsRAN 4G ёмкость считается по среднему CQI выделенной маски (`get_dl_cqi(rbgs)`, `sched_ue_cell.cc:400`)

### BUG-SCH-004 — `_empty_result()` не сбрасывает часть счётчиков статистики
- **Объект:** `PyScheduler/SCHEDULER.py::SchedulerInterface._empty_result` (:1037–1062), `_update_stats` (:1104)
- **Категория:** подозрение на баг
- **Наблюдение:** при досрочном выходе (после этапов 1, 2.5, 4, 5) обнуляются `_last_priority_list_full`, `_last_allocation`, `_last_users` и счётчики eligible/RB/active через `_update_stats(tti, 0, 0, 0)`, но `_last_pdcch_blocked_count` и `_last_avg_priority_value` не трогаются — значения прошлого TTI «залипают» в `get_stats()` (:489–490).
- **Доказательство:** чтение кода :1037–1062 и :1104–1118.
- **Влияние:** метрики пустых TTI недостоверны: по `sch_pdcch_blocked_count`/`sch_avg_priority_value` нельзя отличить «в этом TTI ничего не произошло» от «данные прошлого TTI».
- **Как проверить:** два TTI подряд: полный, затем с пустыми буферами; сравнить поля `get_stats()` до/после.
- **Статус:** подтверждено чтением кода
- **Связь:** пока нет; тривиальный фикс — два сброса в `_empty_result`

### BUG-SCH-005 — `release_cce` — заглушка: CCE «утекают» до конца TTI
- **Объект:** `PyScheduler/SCHEDULER.py::PDCCHManager.release_cce` (:1568)
- **Категория:** долг (осознанный: docstring содержит сценарий применения и пошаговую планируемую логику)
- **Наблюдение:** порядок control-first (этап 5 PDCCH → этап 6 PDSCH) без отката контроля: если после выделения CCE распределение RBG для UE не состоялось, освобождения нет — CCE заняты до `reset_tti()` (:1545) следующего TTI. Для данных откат есть (`RES_GRID::ALLOCATE_RBG` :430 с `RELEASE_RBG` :440), для контроля — заглушка.
- **Доказательство:** код :1568+ («ЗАГЛУШКА для дальнейшей разработки», сценарий «PDCCH выделен, PDSCH не влез»); для сравнения: srsRAN 4G — атомарная транзакция маска+DCI (`sched_grid.cc:134–165`), srsRAN Project — `cancel_last_pdcch` (`pdcch_resource_allocator_impl.cpp:258`).
- **Влияние:** сценарии с дефицитом PDCCH системно искажены: бюджет тратится на гранты, которых не случилось. При малой загрузке мало заметно (сценарий README §4: 2/25 CCE), при экспериментах с малым `max_dl_cce_allowance` или плохим CQI (агрегация 8) — существенно.
- **Как проверить:** искусственный сценарий: малый бюджет CCE + UE, у которого PDSCH заведомо не размещается; сравнить `pdcch_cce_allocated_count` с числом фактических грантов.
- **Статус:** подтверждено
- **Связь:** [FEAT-SCH-001](features.md#feat-sch-001)

### OPT-SCH-002 — AMC: формула вместо таблиц TBS, сдвиг CQI→MCS, учёт CRS и n_ports
- **Объект:** `PyScheduler/SCHEDULER.py::AdaptiveModulationAndCoding` (`CQI_TO_MCS` :1709, `GET_BITS_PER_RB` :1730, TODO :1749–1753)
- **Категория:** долг (осознанное упрощение с TODO в коде)
- **Наблюдение:** (1) Ёмкость RB считается формулой `RE·Qm·R`; TODO в коде: отклонение от таблиц TBS TS 36.213 §7.1.7.2 ~8–10%, план «CQI → I_MCS → I_TBS → TBS_TABLE». (2) `CQI_TO_MCS` по границам модуляций совпадает с TS 36.213 Table 7.2.3-1, но эффективные спектральности смещены: для CQI 5–13 воспроизводится spec-таблица со сдвигом +2 индекса (код CQI 7 = spec CQI 9: 16QAM 0.601), для CQI 1–4 — удвоенные spec-значения, CQI 14–15 экстраполированы за максимум стандарта → ёмкость систематически завышена (CQI 15: 5.87 против 5.55 bit/RE). (3) Учёт служебных RE в `GET_BITS_PER_RB`: из первого слота вычитается целиком `rs_per_slot = 4·n_ports` (:1741–1742), тогда как половина CRS-символов слота 0 уже исключена вместе с PDCCH-областью через `(7 − pcfich)`; для n_ports=4 линейная формула даёт 16 RE на слот вместо фактических 12.
- **Доказательство:** постатейная сверка `CQI_TO_MCS` (:1709–1725) с TS 36.213 Table 7.2.3-1; TODO :1749; issue #30 (вынесен из ревью PR #26). В ветке `feature/HARQ` (commit `eaf4370`) таблицы размеров TB из 3GPP уже добавлены — ветка не слита (последний коммит май 2026). По пункту (3): замечания о двойном вычитании CRS в слоте 0 и о нелинейности при n_ports=4 сделаны в ревью PR #26; правок и отдельного TODO в коде нет (рядом только пометка про зависимость от CP, :1748).
- **Влияние:** абсолютные значения throughput завышены; сравнение алгоритмов между собой предположительно сохраняется (ошибка систематическая) — гипотеза. Блокирует проверку осуществимости гранта (FEAT-SCH-003) и осмысленный бенчмарк оптимума (FEAT-SCH-004). По пункту (3): при дефолтах (pcfich=2, n_ports=1) код даёт 136 RE/RB против 138 по точному расчёту TS 36.211 §6.10.1 (−1.4%) — ошибка разнонаправлена со сдвигом `CQI_TO_MCS` (+5.6% на CQI 15), что затрудняет интерпретацию абсолютных чисел; при MIMO (n_ports=4) линейное `4·n_ports` завысит overhead.
- **Как проверить:** после перехода на TBS-таблицы сравнить `dl_capacity_bits_sum_tti` на эталонных сценариях (в сценарии README §4 сейчас: 13 848 бит ёмкости, 10 408 извлечено); ручной расчёт RE для (pcfich=2, n_ports=1): slot0 = 84 − 24 (PDCCH) − 2 (CRS символа 4) = 58, slot1 = 84 − 4 = 80, сумма 138 против 136 в коде.
- **Статус:** подтверждено (сверка со spec)
- **Связь:** issue #30; [FEAT-SCH-002](features.md#feat-sch-002); ветка `feature/HARQ`; карточка объединяет два прежних наблюдения — формула вместо таблиц TBS и учёт CRS/n_ports (соответствие ID — таблица §1)

### BUG-SCH-009 — Освобождение RBG без проверки владельца: чужие RB освобождаются откатом
- **Объект:** `PyScheduler/RES_GRID.py::RELEASE_RB` (:399 — освобождает любой занятый блок), `RELEASE_RBG` (:440 — вся RBG), `ALLOCATE_RBG` (:430 — откат при частичном отказе), `ALLOCATE_RB_PAIR` (:389 — освобождение непрошедшего слота)
- **Категория:** баг (латентный)
- **Наблюдение:** освобождение не проверяет, кем и чей блок освобождается: `RELEASE_RB` снимает занятость любого блока, `ALLOCATE_RBG` при отказе на любом RB вызывает `RELEASE_RBG` по всей RBG — включая RB, занятые другим UE до текущего вызова; `ALLOCATE_RB_PAIR` при неудаче второго слота освобождает блок, который может принадлежать другому UE. Текущие потоки планировщиков не попадают в это: каждый RBG пробуется не более раза за TTI, `ALLOCATE_RB_PAIR` из планировщиков не вызывается (только самотест RES_GRID :653). Станет рабочим при появлении аллокаторов с retry/rollback; собственный откат поверх отката `ALLOCATE_RBG` удваивает риск — поэтому контракт FEAT-SCH-008 v3 не содержит метода `rollback` у аллокатора, операция `ALLOCATE_RBG` в спецификации не объявляется гарантированно атомарной, а тест сеточного конфликта входит в обязательную регрессию (SPEC-FEAT-SCH-008 §5.3, §9). В v4 для экспериментального и batch-путей добавлена последовательность propose→validate→commit: до фазы commit сетка не меняется вовсе, транзакционный `GridView.commit(plan)` (всё-или-ничего) планируется после исправления этого дефекта, до него commit — последовательные `allocate_rbg` в порядке плана (SPEC-FEAT-SCH-008 §5.6, §12).
- **Доказательство:** воспроизведение на `6c0aae2`: UE A занимает freq 3 RBG 1 в обоих слотах подкадра 5 (`ALLOCATE_RB` ×2 → True); `ALLOCATE_RBG(5, 1, UE B)` → False (частичный отказ на занятом RB); после отката блок A свободен (`CHCK_RB()` = True, `UE_ID = None`) — откат снял чужой ресурс. Чтение кода по ссылкам выше.
- **Влияние:** молча портится сетка: UE теряет выданный RB, сохранив грант PDCCH и место в allocation; на уровне метрик — необъяснимые PRB util и bitmap.
- **Как проверить:** repro выше; направление фикса — проверка владельца в `RELEASE_RB` (`rb.UE_ID == запросивший`) либо откат по списку блоков, выданных внутри вызова. Правка вне объёма FEAT-SCH-008: RES_GRID — чужой модуль (зона PR #33), запрос в [features.md](features.md) §2.
- **Ревью PR #44 — закрыто.** Из docstring `GridView.allocate_rbg`/`LegacyGridView.allocate_rbg` и документации модуля (`README.md` :25, `diagrams.md` :23) убраны ложные утверждения об атомарном откате `ALLOCATE_RBG`. Поведение `RES_GRID` не менялось (R2, A1): owner-safe откат остаётся задачей владельца сетки.
- **Статус:** подтверждено воспроизведением (латентный); ложные гарантии отката в документации и контрактах устранены
- **Связь:** [FEAT-SCH-008](features.md#feat-sch-008) (контракт аллокатора без собственного rollback), [FEAT-SCH-001](features.md#feat-sch-001); RES_GRID PR #33

### CFG-SCH-001 — В `.ruff.toml` не задан `src`: результат линтера зависит от каталога запуска
- **Объект:** `.ruff.toml` (корень репозитория: `line-length = 100`, `target-version = "py310"`, `select = ["E","F","W","I","N","B"]`, `ignore = ["E501"]`, `per-file-ignores = {"*.py" = ["E402"]}`); затронуты все плоские модули `PyScheduler/`
- **Категория:** вопрос / долг (конфигурация репозитория — чужой файл)
- **Наблюдение:** в конфиге не задан `src`, поэтому классификация first-party зависит от cwd: собственные модули проекта (`SCHEDULER`, `BS_MODULE`, `GLOBALS`, `RES_GRID`, …) считаются third-party, и правило порядка импортов (I001) требует одного расположения; при явном `src = ["PyScheduler", "."]` те же модули становятся first-party, и требование меняется на **противоположное**. Дополнительно `E501` (длина строки) внесён в `ignore`, то есть ruff длину строк не проверяет вовсе — ограничение `line-length = 100` приходится выдерживать вручную. Конфиг ввёл PR #8 (`line-length: 1000`, rules `E/F/W/I/N/B`, ignore `E402`+`E501`); на `dev` стоит `line-length = 100`, `E402` перенесён в `per-file-ignores`, а `E501` по-прежнему игнорируется — то есть 100 символов остались соглашением (в ревью PR #8 автор: «пытался держать их в пределе 100 символов на строку»), но не проверкой.
- **Доказательство:** замер 2026-11-01 (ruff 0.17.3, python 3.11.2), дерево `dev@6c0aae2` + патчи M0/fix/M1/выравнивания:

| Запуск | Замечаний по `PyScheduler/` | I001 | Из них в новых каталогах M0/M1 |
|---|---|---|---|
| `ruff check --config .ruff.toml PyScheduler` из корня репозитория | 1095 | 32 | **0** |
| то же с `src = ["PyScheduler", "."]` | 1102 | 39 | 4 (только I001) |
| из `PyScheduler/` с `--config ../.ruff.toml` | — | те же 4 в новых каталогах | 4 |

  Удовлетворить обе конфигурации одним порядком импортов невозможно (проверено на probe-файле: порядок, корректный при `src`, даёт I001 без него, и наоборот). Замечания E/F/W/N/B от `src` не зависят. В `SCHEDULER.py` — 60 замечаний, столько же, сколько на `dev` (0 новых), в строках >3245 — 0.
- **Влияние:** (1) «зелёный» локально прогон ruff может быть «красным» у ревьюера или в будущем CI — результат зависит от того, из какого каталога запущен линтер; (2) новые файлы вынуждены следовать порядку third-party, который сам ruff считает ошибочным при явном `src`; (3) любая будущая правка конфига с добавлением `src` массово переставит импорты (I001: 32 → 39 в замере) — нецелевое изменение по A1, которое нельзя делать «заодно» с содержательным PR.
- **Как проверить:** три запуска из таблицы выше; сравнить списки I001 (`--output-format concise`) до и после добавления `src`. Число замечаний считать по строкам вывода, содержащим `.py:` (`… | grep -c '\.py:'`): concise-вывод ruff добавляет итоговые строки `Found N errors.` и `[*] N fixable…`, поэтому `grep -c .` завышает счёт на 2 и для сравнений не годится. Перезамерено 2026-11-01 на ветке `f14885c` и на чистом `dev@6c0aae2`: `PyScheduler/SCHEDULER.py` — 60/60 (0 новых), `PyScheduler/` целиком — 1095/1095 без `src` и 1102/1098 с `src = ["PyScheduler", "."]` (разница +4 — только I001 в новых каталогах). Эти четыре I001: `tests/baseline/sim_checkpoint.py:41`, `tests/baseline/test_matrix.py:18`, `tests/scheduler_arch_tests/arch_support.py:16`, `tests/scheduler_arch_tests/test_views_m1.py:20`.
- **Текст запроса владельцу репозитория (для отправки ответственным):** «В `.ruff.toml` не задан `src`, из-за чего классификация first-party зависит от каталога запуска: `ruff check --config .ruff.toml PyScheduler` из корня даёт 1095 замечаний (I001 — 32), а с `src = ["PyScheduler", "."]` — 1102 (I001 — 39), причём четыре новых I001 появляются в добавленных тестовых каталогах.
