## 1. Предложения
### FEAT-AMC-001 — Самостоятельный AMC и первый этап TBS

- **Статус:** класс и таблицы вынесены в AMC.py; самостоятельный интерфейс пока не реализован. Контракты предложены по замечаниям куратора, согласование с Тимуром не подтверждено.
- **Проблема сейчас:** AMC хранит Scheduler, читает PDCCH и состояние UE для статистики. Перенос файла с сохранением этой связи не создаёт самостоятельный модуль.
- **Цель:** отделить адаптацию параметров передачи и расчёт размера транспортного блока от распределения ресурсов.
- **Предлагаемое изменение после механического переноса:** отдельным этапом A1 выделить единый TBS и подключить к нему существующий TransportBlock. Затем передавать AMC только конфигурацию значениями; get_stats вынести в независимый сборщик по числовому снимку. Потребители получают статистику через новый scheduler.get_amc_stats().
- **Входит / не входит:** входят TBS-сервис, самостоятельный AMC, перенос TransportBlock, статистический снимок и адаптер AmcView. Активация TBS-aware бюджетов во всех алгоритмах и ACK/NACK выполняются отдельно.
- **Входы и выходы:** CQI→MCS, MCS/rb→TBS в битах, legacy bits/RB с явным AmcConfig. AMC не получает Scheduler, PDCCH, UE или callbacks на их состояние.
- **Зависимости:** AmcView.bits_per_rb из спецификации Тимура, владелец Scheduler, StatsManager/SimulationManager, таблицы GLOBALS. Новый источник статистики и TBS-расширение view требуют согласования.
- **Шаги:** E0 механический перенос выполнен (69 тестов прошли) → A0 baseline → A1 TBS → A2 снимок/статистика → A3 независимый AMC и перенос → A4 адаптер стратегий → A5 итоговая совместимость.
- **Проверка готовности:** после каждого этапа обязательны unit и регрессия назначений, буферов, throughput/EWMA и статистики, отчёт до/после и откат. Нельзя ждать финала для первой проверки.
- **Риски и вопросы:** сейчас старый конструктор с Scheduler и amc.get_stats() сохранены. В целевой самостоятельной реализации они заменяются. Места использования обновляются вместе с реализацией нового контракта. TBS-сервис не равен уже переключённой модели передачи.
- **Ссылки:** [SPEC-FEAT-AMC-001](SPEC-FEAT-AMC-001.md), [схемы](diagrams.md#вынос-amc-из-schedulerpy).

Ниже сохранены прежние предложения по TB и CQI→MCS. При расхождении границ текущего этапа применяется SPEC-FEAT-AMC-001; интеграция передачи описывается отдельно в FEAT-TB-001.

### Добавление ТБ
- **Статус:** обсуждается
- **Проблема сейчас:** мертвый код и костыли. Например: функция _get_active_ue_stats нигде не вызывается. В трех функциях(_apply_pdsch_estimation, _allocate_pdsch, _process_buffers) происходит перерасчет размера.
- **Цель:** Создание единой контейнера между решением планировщиком и тем что уходит в эфир. 
- **Предлагаемое изменение:** добавить @dataclass транспортного блока, определить методы для работы с ним. Так же из ns3 перенести перевод из CQI в MCS. Как это повлияет на архитектуру: рассчет размера блока будет проходить в одном месте, что повлиет на скорость выполнения программы, а также повысит читаемость кода. Так же это повлиет на все sheduler алгоритмы так как сейчас рассчет размера блока в них происходит из вместимости выделенных ресурсных блоков.
- **Входит / не входит:** Изменения затронут только функции модуля и GLOBALS(добавление таблицы размеров транспортного блока), BS_MODULE они не затронут.

class TransportBlock:

### Интеграция CQI->MCS в АМС
**Статус:** обсуждается
- **Проблема сейчас:**  Словарь CQI_TO_MCS возвращает пару «порядок модуляции, кодовая скорость» и используется методом GET_BITS_PER_RB() для приблизительной оценки вместимости ресурсов. Выбранный индекс MCS пока не используется в рабочем расчёте размера транспортного блока.
- **Цель:**   установление цепочки CQI->MCS->TB->TBS
- **Предлагаемое изменение:**  внедрить get_mcs_from_cqi() и его таблицы, закрепить правила обработки входных значений и подключить результат к будущему расчёту TBS. Метод выбирает максимальный MCS, спектральная эффективность которого не превышает эффективность входного CQI.
- **Входит / не входит:** Таблицы спектральной эффективности, валидация CQI и определение контракта выбора MCS.
- **Входы и выходы:** Вход — целочисленный CQI. Для CQI от 1 до 15 выход — целочисленный индекс MCS от 0 до 28. Для значений вне диапазона 0–15 — ValueError.
  Обработка CQI=0 требует согласования: сейчас метод возвращает
  MCS=0; предлагается явно обозначать отсутствие допустимой новой
  передачи. Формат такого результата пока не согласован.
- **Зависимости:** SCHEDULER.py->AdaptiveModulationAndCoding,
  SPECTRAL_EFFICIENCY_FOR_CQI и SPECTRAL_EFFICIENCY_FOR_MCS.
- **Шаги:**
  1. Проверить происхождение и согласованность таблиц CQI и MCS.
  2. Зафиксировать правила выбора MCS и обработки CQI=0.
  3. Проверить входной тип и граничные значения.
  4. Проверить соответствие результатов выбранным таблицам.
  5. Подключить индекс MCS к расчёту TBS
- **Проверка готовности:**
  - Для всех CQI от 1 до 15 результат соответствует принятой
    таблице и правилу выбора.
  - Выбранный MCS имеет максимально допустимую спектральную
    эффективность, не превышающую эффективность CQI.
  - При увеличении CQI индекс MCS не уменьшается.
  - Значения вне диапазона и неподдерживаемые типы отклоняются.
  - Поведение при CQI=0 определено и проверено.
  - Контрольные значения зафиксированы тестами. По текущим таблицам: CQI=1 → MCS=0, CQI=10 → MCS=18, CQI=15 → MCS=28.

def get_mcs_from_cqi(self, cqi: int) -> int:
        """
        Аналог LteAmc::GetMcsFromCqi(int cqi).
 
        Берёт спектральную эффективность для CQI и ищет наибольший MCS,
        спектральная эффективность которого не превышает её.
        """
        if not (0 <= cqi <= 15):
            raise ValueError(f"CQI must be in [0..15] = {cqi}")
 
        spectral_efficiency = SPECTRAL_EFFICIENCY_FOR_CQI[cqi]
        mcs = 0
        while mcs < 28 and SPECTRAL_EFFICIENCY_FOR_MCS[mcs + 1] <= spectral_efficiency:
            mcs += 1
        return mcs
