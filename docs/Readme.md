# AdaptiveModulationAndCoding (AMC.py)

> Ответственный: Влад. Обновлено: 2026-10-30. Проверено по локальным исходникам.
> Состояние: класс вынесен в отдельный файл; зависимость от Scheduler сохранена.

## 1. Назначение

AMC преобразует CQI в индекс MCS и оценивает число информационных бит на пару RB за TTI. Планировщик использует оценку при распределении ресурсов и расчёте бюджета извлечения данных.

## 2. Текущее размещение и ответственность

Класс AdaptiveModulationAndCoding и таблицы SPECTRAL_EFFICIENCY_FOR_CQI/SPECTRAL_EFFICIENCY_FOR_MCS находятся в [AMC.py](../PyScheduler/AMC.py). Прежний импорт через SCHEDULER.py сохранён. TransportBlock находится в TRANSPORT_BLOCK.py; его метод делегирует чистому калькулятору get_tbs_bits в AMC.py. Старый импорт через SCHEDULER.py сохранён.

AMC пока также собирает статистику через ссылку на Scheduler. Он не распределяет PRB, не хранит очереди и не реализует ACK/NACK.

## 3. Входы, выходы и зависимости

| Метод / объект | Вход / зависимость | Результат |
|---|---|---|
| __init__(scheduler=None) | Необязательная ссылка на Scheduler | Сохраняет self.scheduler |
| get_mcs_from_cqi(cqi) | CQI 0–15; таблицы эффективности | Индекс MCS; CQI=0 даёт 0 |
| CQI_TO_MCS | Словарь CQI → (Qm, code rate) | Данные legacy-формулы, не индекс MCS |
| GET_BITS_PER_RB(cqi, n_ports=1) | CQI 1–15; число портов; pcfich через Scheduler, без него 2 | Целое число бит по формуле |
| get_stats() | _last_users, _last_allocation, cqi_map и поля UE через Scheduler | Словарь текущих показателей |

Самостоятельно можно вызвать вычисления с настройкой по умолчанию. Это не делает весь класс независимым: настроенный расчёт и сбор статистики всё ещё связаны со Scheduler.

## 5. Актуальные границы после ревью

Legacy-статистика и конструктор с Scheduler сохранены по решению куратора. Создание AMC_METRICS и удаление get_stats отложены до требований владельца статистики. Добавлены необязательная неизменяемая AmcConfig и интерфейс сменной политики MCS; текущий путь Scheduler не переключён на новый интерфейс или табличный бюджет.

## 1. Назначение
HARQ предназначен для управления повторными передачами транспортных блоков при неуспешном декодировании.
В текущем SCHEDULER.py подготовлены поля HARQ в структурах данных, ссылка на менеджер процессов и метод запроса повторных передач. Полный механизм HARQ не реализован и не участвует в работе schedule().
## 2. Границы ответственности
**Что существует:** 
- Создание и управление HARQ-процессами.
- Сохранение транспортного блока между попытками.
- Обработка ACK/NACK и таймеров обратной связи.
- Переключение NDI и управление RV между попытками.
- Планирование повторов в schedule().
- Ограничение количества попыток и освобождение процесса.
  **Пока отсутвует:**
- Создание и управление HARQ-процессами.
- Сохранение транспортного блока между попытками.
- Обработка ACK/NACK и таймеров обратной связи.
- Переключение NDI и управление RV между попытками.
- Планирование повторов в schedule().
- Ограничение количества попыток и освобождение процесса.

## 6. Ограничения и открытые вопросы
### Подтверждённые ограничения
- harq_manager при создании планировщика равен None.
- _get_harq_retransmissions() не вызывается из schedule().
- Проверка занятости HARQ-процессов в _filter_eligible_ues() закомментирована.
- Наличие полей HARQ не сопровождается управлением их состоянием.
- Данные учитываются как переданные без подтверждения доставки.
- Идентификатор процесса назван harq_id в TB и harq_process_id в SchedulingGrant.
### Требует согласования
- Кто предоставляет ACK/NACK и с какой задержкой.
- Где хранится содержимое TB между попытками.
- Количество процессов и максимальное число попыток.
- Правила изменения RV и переключения NDI.
- Порядок обработки feedback и повторов внутри TTI.
- Учёт повторов, подтверждённой доставки и потерь.
